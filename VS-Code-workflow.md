# AI-Agent Supported Project Coding

## 0.0 One time setup: the `_AgentKit` folder

The canonical files live once, in a single Dropbox folder, and get copied into
each new project. Do this setup once, not per project.

```{text}
Dropbox/Work/_AgentKit/
├── AgentKit_overview.md         <- what the kit is and why it is built this way
├── AgentKit_instructions.md     <- operational rules for editing the kit itself
├── VS-Code-workflow.md          <- this document
├── AGENTS.md                    <- coding/analysis contract (was REFERENCES/instructions.md)
├── academic-writing-style.md    <- writing style skill and profile, always in force
├── new_project.sh               <- scaffolding script (copies these files into a new project)
├── RULES_AND_LOGS/              <- coding rules and the kit's own working history
│   ├── R_Rules.md               <- R and Quarto rules, copied into each project
│   ├── Mplus_Rules.md           <- Mplus rules, copied into each project
│   ├── SESSION_LOGS.md          <- log of work on the kit itself
│   └── DECISIONS.md             <- one line per consequential choice
├── REFERENCES/                  <- kit's own source material
│   └── Jones_Writing_Samples/   <- writing samples the style was measured from
│                                   (local only, not in the public repo)
└── templates/                   <- starter files copied into each new project
    ├── reference_manuscript.docx <- pandoc reference doc, journal manuscript formatting
    ├── reference_proposal.docx   <- pandoc reference doc, grant proposal formatting
    ├── reference_report.docx     <- pandoc reference doc, internal analysis report formatting
    ├── slides_Control.qmd       <- reveal.js deck (QMD to reveal.js)
    ├── slides_Driver.R          <- render script for the deck
    ├── manuscript_Control.qmd   <- DOCX manuscript (QMD to DOCX)
    ├── manuscript_Driver.R      <- render script for the manuscript
    ├── CLAUDE.md                <- pointer so Cowork loads AGENTS.md and the style file
    ├── README.md                <- project quickstart
    └── R/
        ├── 000-Libraries.R
        └── 001-Environment-settings.R
```

Note: Adding an additional document type later (a poster format, say) means
dropping a fourth `reference_<type>.docx` into `templates/`. `new_project.sh`
copies whatever it finds here; it does not hardcode the three names above.

Relevant ancillary programs (`pdf2llm.sh`) are not defined here. Get a copy at
https://github.com/rnj0nes/pdf2llm and symlink it onto your `PATH`. There is no
per project copy to maintain. Appendix 3 has the usage.

This folder is the only place these master files should be edited. Each project
holds its own physical copy, taken at creation. A change here does not reach
projects that already exist. To update an existing project, copy the changed
file in again by hand. The tradeoff is deliberate: no automatic propagation, in
exchange for each project being self-contained and portable.

### 1.1 Set up a new project

```{zsh}
new_project.sh <ProjectName>
```

This single command creates the full folder skeleton, copies in `AGENTS.md`,
`.github/copilot-instructions.md`, `CLAUDE.md`, `README.md`, the slide and
manuscript templates, the R starters, and every typed reference doc from
`_AgentKit`, and opens the project in VS Code if the `code` command is
available. See Appendix 2 for the script itself and the one time setup it
requires.

What is still manual, by design, since it is genuinely project specific:
choosing your driver and control filenames, collecting references into
`REFERENCES/`, and running `pdf2llm` on new PDFs as they arrive.

### 1.2 Driver file and build commands (generic)

Each analysis has one driver, living beside its control file in the analysis
subfolder, and that driver is your run target from a clean session:

- Stata/DOMD workflow: `Stata/<Analysis>/<stem>_Driver.do`
- QMD/R workflow: `R/<Analysis>/<stem>_Driver.R`

Drivers use project relative paths only. In R, reach the project root with
`here::here()`, which resolves against the `.here` marker and works from any
working directory. In Stata, set the working directory to the project root
explicitly, since there is no equivalent.

#### 1.3 Example: Stata driver for `.domd` workflow

Use this pattern when your report source is `<analysis>_Control.domd` and
you need `pandoc` for DOCX reference formatting.

The driver lives in `Stata/<Analysis>/` beside its control file, mirroring the
R side. Stata has no equivalent of `here::here()`, so the working directory is
set explicitly, and it is set to the project root rather than to the analysis
folder so that output paths match the R workflow.

```{stata}
* Stata/<Analysis>/<stem>_Driver.do
* Set the working directory to the PROJECT ROOT, two levels up from this file.
cd "`c(pwd)'/../.."

local analysis "Project1"
local stem     "manuscript"
local src      "Stata/`analysis'"

* note: must include the `keep` option to save the intermediate markdown file
* for the second pandoc run to format references in the Stata workflow
markstat using "`src'/`stem'_Control.domd" , keep strict bundle docx

!/usr/local/bin/pandoc "`src'/`stem'_Control.md" --citeproc \
    --reference-doc=TEMPLATES/reference_report.docx \
    -o "`src'/`stem'_Control.docx"

* Move into the flat RENDER/, prefixed by the analysis so two subfolders
* cannot collide, then copy into REPORTS/ with the render date.
!mkdir -p RENDER REPORTS
!mv "`src'/`stem'_Control.docx" "RENDER/`analysis'_`stem'.docx"
!cp "RENDER/`analysis'_`stem'.docx" "REPORTS/`analysis'_`stem'_$S_DATE.docx"

* Clean up intermediates. Leftover .md and .do files in the analysis folder
* will confuse the agent.
!rm -f "`src'/`stem'_Control.md" "`src'/`stem'_Control.do" \
       "`src'/`stem'_Control.pdx" "`src'/`stem'_Control.smcl"
```

MacOS CLI command to run the driver:

```{zsh}
/Applications/Stata/StataMP.app/Contents/MacOS/stata-mp -b do Stata/<Analysis>/<stem>_Driver.do
```

If you use a different Stata edition, swap `StataMP` for `StataSE` or
`StataBE` in the command above.

#### 1.4 Example: R driver for `.qmd` workflow

Use this pattern when your report source is `R/<Analysis>/<stem>_Control.qmd`.
The driver sits beside it in the same folder and runs from anywhere, because
every path resolves from the project root through `here::here()`.

```{r}
# R/<Analysis>/<stem>_Driver.R

analysis <- "Project1"
stem     <- "manuscript"
src_dir  <- here::here("R", analysis)

quarto::quarto_render(
  input       = file.path(src_dir, paste0(stem, "_Control.qmd")),
  output_file = paste0(stem, "_Control.docx")
)
```

The full pattern, including the move into `RENDER/` and the dated copy into
`REPORTS/`, is in `templates/manuscript_Driver.R` and section 10 of
`RULES_AND_LOGS/R_Rules.md`. Never add `--output-dir`: Quarto empties whatever
directory it is given, and `RENDER/` is shared by every analysis.

For DOCX output in QMD workflows, configure `reference-doc` in the YAML
header of the control file, choosing whichever of `reference_manuscript.docx`,
`reference_proposal.docx`, or `reference_report.docx` matches the document you
are producing. All three are copied into the project's `TEMPLATES/` folder at
creation, so from `R/<Analysis>/` the YAML path is
`../../TEMPLATES/reference_manuscript.docx`. YAML cannot call `here::here()`,
which is why that one is literal.

Those copies belong to the project and are meant to be restyled in Word as often
as the work requires. If you rebuild one starting from a real manuscript, it
carries that manuscript's text, citation keys, and cited DOIs inside the file,
where Word does not show them and pandoc ignores them. Run
`scrub_reference_docs.py` over it before the project is shared.

The scaffold also drops in a ready `manuscript_Control.qmd` and
`manuscript_Driver.R`. Rename them to your analysis slug, update the `input =`
line in the driver, then render with `source("<analysis>_Driver.R")`.

#### 1.45 Example: reveal.js slides

Slides use the same driver and control pattern, with `format: revealjs` in the
control file instead of `format: docx`. The scaffold provides
`slides_Control.qmd` and `slides_Driver.R` for this. The control file carries
the reveal.js YAML and CSS and pulls in content slides with `{{< include >}}`:

```{text}
{{< include R/031-content-slides.qmd >}}
```

Write each topic as its own `.qmd` in `R/`, using `##` to start each slide.
Render from the project root:

```{r}
source("slides_Driver.R")   # after renaming to <analysis>_Driver.R
```

The driver renders beside the control file as a single self-contained HTML file
with images embedded, moves it into `RENDER/` under the analysis-prefixed name,
and copies a dated version into `REPORTS/`.

The title-slide watermark is commented out in the template, because the scaffold
does not create the image and Quarto fails rather than warns on a missing
background. To use one, drop an image at `FIGURES/watermark.png` and uncomment
the four `title-slide-attributes` lines.

### 1.5 ADMIN

`ADMIN/` holds the project's administrative record rather than anything that
feeds an analysis or a document. Data use agreements, IRB and regulatory
correspondence, sponsor and collaborator email, signed forms, approvals, and
amendments all belong here.

The agent contract treats this folder differently from every other. An agent
reads a file in `ADMIN/` when you point it at one and will answer questions
about it, but it does not search the folder when looking for support for a
claim, does not treat it as grounding material, and does not quote or paraphrase
it into a manuscript, proposal, report, or slide unless you ask for exactly
that. The reason is the content: these files carry other people's names and
contact details, and agreements carry confidentiality terms.

If a project is ever shared or made public, this is the first folder to check.

### 1.6 Reference docs

There is no single `reference.docx` anymore. Different document types need
different pandoc reference formatting (margins, heading styles, page
numbering), so `_AgentKit/templates/` holds one typed reference doc per document type:
`reference_manuscript.docx`, `reference_proposal.docx`,
`reference_report.docx`. `new_project.sh` copies whichever of these exist into
every new project's `TEMPLATES/` folder, under their own names, with no need to
declare a type up front. Pick the relevant one by name in the YAML or
pandoc command for a given render, and nothing stops one project from
producing both an internal report and, later, a manuscript from the same
control file, just by rendering twice with two different reference docs.

The copies in `TEMPLATES/` belong to the project and are meant to be restyled.
A journal with its own heading and margin requirements gets a reference doc
edited to match, and because the files are copies, that affects the one project
and nothing else.

One caution when restyling. Building a reference doc by starting from a real
manuscript brings that manuscript's text, citation keys, and cited DOIs into the
file, in places Word does not display and pandoc ignores. Nothing looks wrong
and nothing renders wrong. Run `scrub_reference_docs.py` from `_AgentKit` over
the file before the project is shared or made public.

### 1.7 References and agent instructions

(1) Collect your references and source material and place copies in
`./REFERENCES`.
(2) Shorten the filenames (e.g., `Jones-2003.pdf`).
(3) Run `pdf2llm` on all the PDFs (see Appendix 3).
(4) If you add more references later, follow the steps above on the new
material, and let your agent know.

`AGENTS.md` and `.github/copilot-instructions.md` need no setup here. They
were copied in when you ran `new_project.sh`.

### 1.8 Using your Agent

Open your AI-agent-supported IDE (e.g., VS Code) in the project folder, or
let `new_project.sh` do it for you. Copilot Chat reads
`.github/copilot-instructions.md` automatically on every chat request in that
workspace, for whichever model you have selected in the model picker.

`AGENTS.md` is a separate case and needs a one-time setting. VS Code reads it
only when `chat.useAgentsMdFile` is true, since that support is experimental and
off by default. Turn it on in Settings, or the coding contract will not load and
you will get the writing style alone without any sign that half the instruction
set is missing. Right-click in the Chat view and choose Diagnostics to see which
instruction files actually loaded.

With that setting on there is no prompt to paste and no reload step at the start
of a session.

If you work in Cowork instead of VS Code, the two instruction files are not
loaded automatically. The scaffold adds a `CLAUDE.md` at the project root that
tells the agent to read `AGENTS.md` and `.github/copilot-instructions.md`
first. Point Cowork at the project folder and, at the start of a session, ask
it to read `CLAUDE.md`. That gives it the same contract and writing style
Copilot gets automatically. Since this project moves between both, keep both
paths in mind: VS Code loads the files on its own, and Cowork needs the
`CLAUDE.md` pointer.

One of the first things you might still ask your agent to do is build a
bibtex file, updating `./bibliography.bib` from the contents in
`./REFERENCES`, and to use it when citing the reference literature. Tell
your agent to use APA or AMA style references, and to cite specific page
numbers from the source material when needed.

### Appendix 3: How to use pdf2llm.sh

Get a copy at https://github.com/rnj0nes/pdf2llm. Since it already lives on
your `PATH`, there is no install step here, only usage.

Mac usage:

```{bash}
# run inside REFERENCES so output lands in REFERENCES/LLM_OUT
cd REFERENCES
pdf2llm.sh -o LLM_OUT MyGrant.pdf
```

To apply `pdf2llm` to all PDFs in a folder at once:

```{zsh}
cd REFERENCES
for f in *.pdf; do pdf2llm.sh -o LLM_OUT "$f"; done
```

Keep the `-o LLM_OUT` on every call. Without it the tool writes to `llm_out/`,
which resolves to the same folder on a case-insensitive macOS volume and to a
second, wrong folder anywhere case-sensitive. The contract expects
`REFERENCES/LLM_OUT/`.

If references trickle in over the life of a project rather than arriving
all at once, rerun this loop, or run `pdf2llm.sh` on just the new file. A
folder watcher that triggers automatically on file drop is a reasonable
future addition if this becomes frequent enough to be worth the extra
moving part; it is not included here since the loop above is one line.

### Appendix 4: Academic writing style integration

`.github/copilot-instructions.md` in each project is a physical copy of
`_AgentKit/academic-writing-style.md`, which holds the same content as the
Codex skill at `~/.codex/skills/rich-jones-academic-writing/`. Copilot Chat
combines this with `AGENTS.md` automatically and applies it to every chat
request in the project, including narrative prose inside `.qmd` and `.domd`
files, regardless of which model is selected in the picker.

This file needs no `applyTo` frontmatter. That requirement is specific to
the path-scoped `.github/instructions/*.instructions.md` format, which
exists for rules that should apply only to certain file types. Since the
writing style applies everywhere, the simpler, always-on
`copilot-instructions.md` format is the right fit.

`references/style-profile.md` in the Codex skill is a copy of
`academic-writing-style.md` in `_AgentKit`. Under the copy model these two can
drift, so re-copy the master into the Codex skill whenever the style changes:

```{zsh}
cp ~/Library/CloudStorage/Dropbox/Work/_AgentKit/academic-writing-style.md \
  ~/.codex/skills/rich-jones-academic-writing/references/style-profile.md
```

`~/.codex` sits outside Dropbox, so nothing syncs it for you. After the move to
Ubuntu, run this same copy with whatever paths are correct there. The master
itself travels safely as part of the Dropbox folder.

`SKILL.md` itself still has one line worth trimming, the one telling Codex
to "use the full style profile in references/style-profile.md when the
task involves substantial drafting...". That instruction made sense when
the profile was a separate, more detailed file Codex would consult only for
heavier tasks. Now that the profile is this same always-loaded file, the
line is circular rather than wrong, harmless to leave, but worth cutting if
you are in there anyway.

#### 5.2 Custom styles

The `Commentary` style uses the nice excalifont.

**Anticipated problems** This analysis is limited to participants without major neurocognitive disorder (MND) because the DEL-S was developed in BASIL I participants without MND, and the BASIL II validation aim for the DEL-S is focused on participants without ADRD [@r01basil2019, pp. 4, 11].

#### 5.3 Footnotes

**Example 1**

```{text}
This sentence has a footnote reference.[^1]

[^1]: This is the footnote text.
```

**Example 2**

```{text}
This sentence has a footnote reference.[^And, the footnote is not directly numbered and the footnote contents are embedded in the paragraph]
```

The document will compile with a numbered footnote and "And, the footnote is
not directly numbered and the footnote contents are embedded in the
paragraph" as the footnote text.
